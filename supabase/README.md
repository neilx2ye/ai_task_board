# Supabase database

These files target a hosted Supabase project. They do not require, configure, or
ship a local/self-hosted PostgreSQL service.

Apply the migrations in filename order:

1. `20260808000000_initial_schema.sql` creates enums, tables, indexes, foreign
   keys, tree/DAG validation triggers, application-level append-only task events, and Auth-user
   workspace onboarding. It immediately enables fail-closed RLS and removes
   Data API privileges; the final policies and grants arrive in migration 3.
2. `20260808000100_core_functions.sql` creates the transactional task, session,
   connection, message, dependency, lease, aggregation, and idempotency RPCs,
   then revokes their default `PUBLIC` execution privilege in the same migration.
3. `20260808000200_rls_storage.sql` enables RLS, applies explicit column/table
   privileges, enables Realtime publication, creates the private
   `task-artifacts` bucket, and installs its object policies.
4. `20260808000300_session_directed_dispatch.sql` adds session-directed user
   turns and the atomic per-session dispatch contract.
5. `20260809141451_session_conversation_bridge.sql` adds the append-only
   Session activity stream, Web conversation RPCs, and Bridge wake support;
   `20260809141643_session_activity_fk_indexes.sql` adds its foreign-key
   indexes.
6. `20260809150155_heartbeat_idempotency_maintenance.sql` separates heartbeat
   refreshes from durable idempotency records and installs bounded cleanup.
7. `20260810100000_bridge_v2_thread_inventory.sql` adds device/thread inventory,
   authoritative activity fencing, and effective device presence.
8. `20260810130000_bridge_remote_configuration.sql` adds Owner-managed desired
   Bridge settings plus token-authenticated, runtime-leased effective status.

For a linked development project:

```bash
npx supabase login
npx supabase link --project-ref <development-project-ref>
npx supabase db push --linked
```

To include demo data, first create a development Auth user, then apply
`supabase/seed.sql` with the Supabase SQL editor or the CLI's linked-project seed
workflow. Never seed a production project. The seed creates the five-step
“完成竞品研究报告” tree and the three offline demo sessions. It never inserts an
`auth.users` row. If run before a user exists, re-running it after signup attaches
the existing demo workspace to the first development user.

## Local PostgreSQL quick deploy

For a disposable local database (not hosted Supabase), the whole schema applies
with one command:

```bash
DATABASE_URL=postgresql:///ai_task_board_local npm run db:local
# with demo data:
DATABASE_URL=postgresql:///ai_task_board_local npm run db:local:seed
```

The script requires `psql` and `createdb` on PATH and a running PostgreSQL
server. It creates the target database when missing, applies
[`supabase/local/bootstrap.sql`](local/bootstrap.sql) (the
anon/authenticated/service_role roles, `extensions.gen_random_uuid`, and the
minimal `auth`/`storage` compatibility schemas the migrations expect), then
applies every file in `supabase/migrations/` in filename order, each inside its
own transaction. Applied filenames are recorded in
`supabase_migrations.schema_migrations`, so re-runs skip finished work and a
later `supabase db push` against the same database does not re-apply history.

This path prepares the **database** only. Supabase Auth, Realtime and hosted
Storage are services, not schema objects: an application connected to a plain
local PostgreSQL still needs its own auth, change-push and file backends. The
bootstrap keeps RLS definitions intact for defense in depth; applications that
connect as a superuser-equivalent role bypass them, matching the hosted
`service_role` path.

## Security contract

- Connection and claim tokens are generated by the Next.js server. Only their
  peppered hashes are passed to RPCs and stored. Raw tokens must never be passed
  in SQL parameters.
- `claim_token_hash` and `api_token_hash` are not granted to `authenticated`;
  RPC payloads also remove them before returning JSON. The Realtime publication
  uses an explicit `tasks` column list that omits `claim_token_hash` and rejects
  an unsafe `FOR ALL TABLES` publication configuration.
- Business tables are browser-readable only through workspace RLS. Browser
  writes are denied; all state/dependency/result changes use the RPCs.
- AI and user command RPCs are executable only by `service_role`; every RPC
  independently checks the supplied workspace/connection/session or user
  membership context.
- Storage names must be exactly
  `<workspace_uuid>/<task_uuid>/<uuid>-<safe_filename>`. The bucket is private.

## RPC response shapes

Business commands return `jsonb` and cache that JSON for 24 hours by
`(workspace_id, actor_key, idempotency_key)`. Reusing a key with another
operation or request hash raises `IDEMPOTENCY_CONFLICT`. High-frequency
Session/claim heartbeats are naturally idempotent state refreshes: they validate
the request-key contract but do not cache responses or append heartbeat events.
An empty `claim_next_task` poll also takes a no-write fast path; a real claim is
still cached and replayable after completion. Supabase Cron removes expired
cache rows every ten minutes in bounded batches.

- `register_ai_session` → `{ "session": ... }`
- `sync_ai_sessions` → `{ "connection": ..., "sessions": [...] }`
- `exchange_ai_connection_bridge_config` → `{ "configuration": ... }`
- `update_ai_connection_bridge_config` → `{ "configuration": ... }`
- `report_current_task`, `claim_next_task`, `claim_task`, `heartbeat_claim`,
  `report_progress`, `release_task`, `fail_task` → `{ "task": ... }`
- `create_subtasks`, `create_user_subtasks` →
  `{ "parent_task": ..., "subtasks": [...] }`
- `request_user_input`, `post_task_message`, `post_user_task_message`,
  `reply_to_task` → `{ "task": ..., "message": ... }`
- `complete_task` → `{ "task": ..., "message_id": ..., "artifacts": [...] }`
- `complete_task_and_claim_next` adds `"next_task": null | ...` to the complete
  response and prefers runnable work under the same root task.
- Connection commands → `{ "connection": ... }` without its token hash.
- `create_user_artifact` → `{ "artifact": ... }`; its path must use the
  artifact id as the filename UUID prefix.

Every artifact has exactly one location: a private `storage_path` or an HTTPS
`external_url`, never both and never neither.

The application may merge a deterministically generated raw claim/connection
token into its HTTP response. The database never stores raw token material.
Every AI RPC, including `register_ai_session`, also receives the server-derived
`p_api_token_hash` immediately after `p_connection_id`. PostgreSQL rechecks that
hash while holding the connection's shared transaction lock; revoke/rotate take
the matching exclusive lock, so an old-token write cannot enter after rotation.

`create_subtasks` is an all-at-once AI split and requires the claimed parent to
be a leaf. `create_user_subtasks` may append to an existing aggregation parent,
provided the parent itself has no active claim. `depends_on` entries resolve
either batch-local `client_ref` values or existing same-workspace task UUIDs.
Turning a leaf into an aggregate clears both its claim and direct session
assignment; a session waiting on that former leaf is recalculated immediately.
An aggregate can never receive a new direct assignment through
`update_user_task`; a null assignment patch is still accepted to repair a
historically inconsistent aggregate and recalculates its former session.
Any prerequisites already attached to the parent are retained as inheritance
metadata and copied onto every direct child, including children appended by a
later request. Thus planning a blocked task never makes its leaves claimable
before the original prerequisites complete.

While a task is `waiting_user`, its assigned AI session remains the preferred
responder. A user may clear that assignment (which recalculates the old session
status), but cannot reassign the pending question to another session. A pending
question must be replied to or cancelled before that leaf can be split into
subtasks, so its required-response message cannot become stranded on an
aggregation-only task. Cancelling a task atomically closes unread
required-response messages in the cancelled subtree while preserving their
content and cancellation events.

Claims hold a shared workspace scheduling lock. Completion-boundary changes
(complete, reopen, cancel, split, aggregate propagation, and physical task
cleanup) hold the matching exclusive transaction lock. This serializes
dependency readiness checks without removing `SKIP LOCKED` claim concurrency
between independent sessions, and prevents an active downstream task from
losing a completed prerequisite mid-run.
Within that lock, AI commands consistently lock session before task; user and
maintenance commands that discover sessions from task rows use exclusive state
ownership. Physical row deletion uses a fail-fast state try-lock so it cannot
wait in the inverse order.
An expired-claim takeover also locks the former session with `SKIP LOCKED`;
transient cross-takeover contention returns `TASK_ALREADY_CLAIMED` and rolls
back the idempotency reservation, so the same request key can be retried safely.

The seed connection's hash is deliberately unusable with application token
derivation. Create a real connection in the Web UI for REST or MCP demos.
